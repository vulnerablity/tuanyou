# 收藏 / 关注 / 点赞 / 报名（含取消）前端性能优化方案

## 一、请求层优化（降低网络压力，防止狂点打满请求）
### 1、按「业务+资源ID」粒度做请求锁（Map 存储）
不同资源互不干扰，比如笔记A点赞请求中，笔记B可以正常点击，不会被错误锁住。

- 点击时先判断 `pendingReq.has(key)`，存在直接return，阻止重复发请求
- 请求finally中删除key，无论成功失败释放锁

### 2、AbortController 丢弃过期未完成请求
用户快速连续点击切换，**终止上一个pending请求，只保留最新操作**，释放浏览器http连接，减少后端无效消耗。
> 注意捕获 `AbortError`，该异常属于主动取消，**不计入业务错误监控**。

### 4、区分两种交互模式
1. **点赞、取消点赞、收藏、取消收藏、关注、取消关注：乐观更新**
点击立刻修改UI状态、数字，不等接口返回；请求失败必须回滚UI状态。体验好，消除接口RT带来的卡顿。
2. **报名/取消报名：谨慎乐观更新**
报名属于高权重业务，涉及资格、名额；**一般不做乐观更新**，等待接口返回再更新UI，可做按钮loading态提示用户正在处理。

## 二、渲染层性能优化（防止高频点击引发页面卡顿）
1. **列表局部更新，杜绝全列表重渲染**
瀑布流/长列表中，点赞收藏状态变化，**只更新当前这条Item，不要触发整个列表组件重渲染**。
- React/Taro：把每条列表拆成独立子组件；状态下沉到item，上层列表不要存每条的交互状态。
- 避免把点赞状态和点赞数等数据放到父组件state，点击修改造成整个列表re‑render。

1. 避免频繁布局偏移 CLS
按钮状态切换（变色、数字变化）预留DOM空间，不要因为状态变化造成页面跳动，提升CLS指标。

1. 回调优化
不要在render内动态生成匿名回调，避免不必要闭包，减少GC压力。

1. 按钮Loading状态区分
- 点赞收藏：不置灰，UI视觉直接乐观变更；内部请求锁拦截重复点击
- 关注、报名：展示loading图标，按钮置半透明，明确告知用户请求正在处理

## 三、异常与监控（前端性能岗位重点）
### 埋点&性能观测指标
1. 各个toggle接口：RT、成功率、429限流占比
2. **乐观更新回滚埋点**：点赞/收藏/关注发生UI回滚时上报，回滚率高代表弱网、后端异常
3. 埋点统计短时间高频点击行为，识别用户暴力点击场景
4. 监控点击后JS执行耗时、布局重排耗时

> 错误过滤：AbortController产生的AbortError，过滤，不要污染错误看板。


## 五、各操作方案汇总表
| 操作          | 请求锁    | AbortController | 乐观更新 | UI表现                                |
| ------------- | --------- | --------------- | -------- | ------------------------------------- |
| 点赞          | ✅按资源ID | ✅               | ✅        | 点击立刻变色，失败回滚                |
| 收藏          | ✅按资源ID | ✅               | ✅        | 点击立刻变色，失败回滚                |
| 关注          | ✅按资源ID | ✅               | ✅        | 可展示loading，失败回滚               |
| 报名/取消报名 | ✅按资源ID | ✅               | ❌不推荐  | 等待接口返回再变更UI，按钮loading置灰 |

## 六、完整流程示例（点赞，乐观更新）
1. 用户点击点赞按钮 → 生成key，判断pendingMap，正在请求直接拦截
2. abort上一次未完成请求
3. 乐观变更本地UI状态、计数
4. 设置pending标记，发起toggle请求
5. 成功：不操作；失败：回滚UI状态，上报回滚埋点
6. finally：清除pending标记

> 报名流程（无乐观更新）
1. 用户点击报名，加请求锁、abort旧请求，按钮loading置灰
2. **不改动UI**，直接发请求
3. 接口成功 → 更新UI；失败弹出toast提示
4. finally释放锁，关闭loading
